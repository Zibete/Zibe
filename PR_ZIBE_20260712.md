# 🧭 refactor(pre-scale): complete architecture and coherence review before scaling

Base: `main`
Rama: `refactor/pre-scale-coherence-review`

## 📌 Resumen ejecutivo

- Congela los comportamientos críticos actuales antes del refactor.
- Alinea toolchain, dependencias y compatibilidad Android 16 KB.
- Refuerza límites `app -> domain <- data`, manteniendo `core` como infraestructura compartida.
- Extrae operaciones de chat, reduce responsabilidades de presentación y formaliza contratos DM/Firebase.
- Unifica efectos UI, snackbar y propagación de errores/cancelación.
- Amplía cobertura JVM, instrumentada, Functions, Rules y checks arquitectónicos en CI.
- Documenta arquitectura, decisiones, contratos, riesgos y operación segura para agentes.

## 🧩 Problemas de partida

- Dependencias y configuración Android dispersas, con versiones desalineadas y librerías nativas incompatibles con páginas de 16 KB.
- ViewModels acoplados a tipos Android y repositorios concretos.
- `ChatViewModel` concentraba persistencia, estado, media y detalles de plataforma.
- Contrato DM implícito: IDs ambiguos, estados delivery/receipt/seen, fan-out, unread y borrado sin una especificación verificable única.
- Manejo heterogéneo de errores, snackbar y cancelación de corrutinas.
- CI sin evidencia completa para Functions, Rules, límites de módulos, androidTest/Hilt y release Kotlin.

## 🏗️ Arquitectura final

- `app`: composición Android, Activities/Fragments/Compose, ViewModels y adaptadores de plataforma.
- `domain`: contratos y operaciones puras; no importa Android, Firebase ni implementaciones de `data`.
- `data`: implementaciones Firebase/RTDB/Storage y traducción de fallos a `ZibeResult` o `Flow`.
- `core:common`: modelos/utilidades compartidos y compatibilidad legacy explícita; no depende de `app` ni `data`.
- `core:designsystem`: componentes visuales reutilizables.
- Hilt mantiene el wiring en `app/di`; `scripts/check_architecture.py` hace exigibles los límites principales.

## 🔄 Cambios funcionales intencionales

- El envío DM crea `MSG_DELIVERED`; sólo el receptor Android puede promover a `MSG_RECEIVED`, y el thread activo puede promover a `MSG_SEEN`.
- Los fan-outs DM usan una actualización raíz atómica y timestamps del servidor.
- Los UIDs con `_` usan el delimitador de chat ID `|`; el formato legacy `_` queda limitado a pares no ambiguos.
- El borrado DM es soft-delete por rol; no se permite eliminación física del mensaje.
- `activeThread` renueva su lease cada 60 segundos y Functions considera 120 segundos.
- El callback FCM queda acotado a 8 segundos y conserva payload fallback.
- La solicitud de notificaciones se inicia desde una acción contextual hacia Settings, no durante el arranque.

## 🧷 Comportamientos preservados

- Login, onboarding, restauración y conflicto de sesión.
- Navegación principal y flujos existentes de perfil, favoritos, usuarios y grupos.
- Mensajes DM de texto, foto y audio, timeline y estados visibles.
- Contratos Firebase históricos compatibles cuando el chat ID legacy no es ambiguo.
- Jetifier permanece habilitado porque todavía existe una dependencia legacy que lo requiere.

## 🔥 Contrato DM/Firebase

- Creación: `MSG_DELIVERED`; receipt: Android receptor; seen: thread activo.
- Transiciones monotónicas y campos inmutables protegidos por Rules.
- Fan-out raíz atómico: mensaje, resumen sender y resumen receiver.
- `createdAt` y ambos `lastMessageAt` usan `ServerValue.TIMESTAMP`.
- El sender sólo puede incrementar unread del receiver exactamente en uno y resetear seen para el último mensaje.
- Los resúmenes preservan campos owner-controlled; receipt sólo cambia `seen` con el resto idéntico.
- Chat IDs ambiguos con múltiples underscores quedan bloqueados; se requiere inventario/migración antes de desplegar Rules.
- Soft-delete por rol y tombstone `*_BOTH_DLT`; no hay eliminación física.
